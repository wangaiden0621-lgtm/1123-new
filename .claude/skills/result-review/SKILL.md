# 結果檢討

> 這是**挖空模板**。標 ★ 的地方要你自己填。
> 重點是「看到什麼現象 → 代表什麼問題 → 下一次怎麼改」，讓 AI 像店長一樣檢討。

## 什麼時候用

每跑完一次 `npm run simulate`，要決定下一版策略怎麼改時。

## 試算結果裡有哪些線索

試算工具每天會印出：客人數、收入、備貨、宣傳、報廢（清潔費）、淨利、任務、星等、資金，以及「沒買到的客人」：

| 線索 | 意思 |
|---|---|
| 賣完買不到 | 有人想買，但貨不夠 |
| 嫌太貴 | 價格超過客人剩下的預算 |
| 想吃的沒上架 | 客人想吃的菜今天沒賣 |
| 因為討厭的菜不進門 | 上架了某位客人討厭的菜 |

## 對症下藥表

| 看到的現象 | 代表的問題 | 下一次怎麼改 |
|---|---|---|
| 賣完買不到很多 | 備貨太少 | 那樣菜多備一些（注意合計不能超過 80 份） |
| 報廢 15 份以上 | ★ 實際觀察：看是哪幾樣菜報廢（盤點的 waste）。可能原因（推測）：那樣菜備太多、價格擋掉客人、或當天來客變少 | ★ 照盤點「明天建議備貨」（賣出＋沒買到）減少份數；報廢 16 份以上還會多付 50 元大型廚餘清運費，優先處理 |
| 嫌太貴很多 | ★ 實際觀察：「嫌太貴」的人數與當天定價。可能原因（推測）：價格超過客人剩下的預算 | ★ 依 pricing-rules 心法 1 測試降價，寫出每份少收多少，下一版比較多賣的份數是否補得回來 |
| 想吃的沒上架很多 | ★ 實際觀察：「想吃的沒上架」人數。可能原因（推測）：客人的第一順位菜當天沒賣；他們沒買到也算不滿，會拉低星等 | ★ 考慮換上這些客人想吃的菜（最多上架 4 樣），換掉賣最差的那樣 |
| 因為討厭的菜不進門 | ★ 實際觀察：不進門人數。可能原因（推測）：上架了某些客人討厭的菜，他們直接不進店（不算進店客人） | ★ 比較那樣菜賣出的份數和因它流失的客人，賣得少就考慮下架 |
| 星等往下掉 | ★ 實際觀察：當天滿意／不滿的比例（規則書：滿意 < 30% 或不滿 ≥ 25% 就降）。可能原因（推測）：缺貨、沒上架、價格高於建議售價讓買到的人也只算普通 | ★ 先處理造成「不滿」最多的那一項；星等降會讓隔天來客倍率變小（例：3 顆 ×1.0 → 2 顆 ×0.8） |
| ★ 我自己發現的現象：宣傳後增加來客，但淨利未改善 | ★ 實際觀察：先核對新增收入、新增成本與宣傳費（新增淨利 ＝ 收入增加 − 備貨成本增加 − 宣傳費 − 清潔費增加），都要寫算式。可能原因（推測）：多來的客人買不到（缺貨）、想吃的沒上架或嫌太貴，或多備的貨變成報廢 | ★ 核對後才決定：多來的客人沒買到 → 先補貨或調整菜色再宣傳；收入增加小於宣傳費 → 下一版改回不宣傳或改用較低的宣傳費 |

> 表格裡「可能原因」都是推測；回報時要分開寫「實際觀察（試算結果的數字）」和「推測原因」，不能把推測寫成事實。

## 步驟

1. 讀試算結果，逐天找出上表的現象
2. 每一個現象，照對症下藥表提出一個修改
3. **一次最多改 3 個地方**，這樣才知道是哪個修改有效
4. 把修改後的策略存成新的檔案（例如 `plans/v2.json`），不要覆蓋舊的，方便比較

## 回報格式

```text
這一版的結果：最終資金 …、星等 …、報廢 …
發現的問題：
1. 第 N 天：（現象）→（問題）
修改：
1. …
下一版檔名：
```

## 不准做的事

- 不准修改遊戲檔案（`src/` 底下的任何檔案、客人包）
- 只能新增或修改 `web-lab/plans/` 裡的策略檔
