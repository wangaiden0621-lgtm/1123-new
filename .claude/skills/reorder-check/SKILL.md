# 補貨檢查

> 這是**挖空模板**。標 ★ 的地方要你自己填。
> 重點是「數字一定要從盤點資料抄，不能自己編」，而且每個數字都要能驗算。

## 什麼時候用

- 跑完 `npm run simulate`，要決定下一版策略每樣菜備幾份時
- 在瀏覽器玩完一天，想看「倉庫盤點」頁的結果該怎麼調整時

## 資料從哪裡來

在 `web-lab` 資料夾執行：

```text
npm run simulate -- plans/策略檔.json --json
```

每一天的 `inventory` 欄位，是那天每樣上架的菜的盤點：

| 欄位 | 意思 | 怎麼驗算 |
|---|---|---|
| `name` | 菜名 | — |
| `stocked` | 早上備了幾份 | 策略檔裡的 `qty` |
| `sold` | 賣出幾份 | 打烊報表 |
| `waste` | 報廢幾份 | 備貨 − 賣出 |
| `missed` | 賣完之後，還有幾位客人想買卻沒買到 | 客人卡片上「賣完了」的數量 |
| `status` | `ok` 正常、`out` 缺貨、`over` 報廢過多 | 規則書「倉庫盤點」 |
| `suggest` | 明天建議備幾份 | 賣出 ＋ 沒買到 |

## 步驟

1. 執行上面的指令，讀每一天的 `inventory`
2. 先驗算：`waste` 有沒有等於 `stocked − sold`？對不上就停下來回報，**不要用錯的資料做建議**
3. 挑出 `status` 不是 `ok` 的菜
4. ★ 建議備貨量要不要再調整（例如：明天客人比較多的日子，要不要多備幾份？多備幾份？）：
   - 只針對 `status` 是 `out`（缺貨）或 `over`（報廢過多）的菜提出調整；`ok` 的菜不提建議
   - **基礎建議**：依規則書，賣出 ＋ 賣完後沒買到，寫出算式（例：10 ＋ 3 ＝ 13）
   - **隔日調整**要和基礎建議分開寫，而且必須說出證據來自哪裡（例如規則書的天氣／事件、宣傳費、星等對來客數的倍率），再寫出算式
   - 沒有隔日需求的證據 → 只給基礎建議，**不自己加固定百分比**
   - 某一筆資料缺漏或互相矛盾 → 寫出第幾天、哪樣菜、哪個欄位有問題，**停止提出這一筆的建議**；其他正確的資料照常分析
5. ★ 同一樣菜連續幾天都缺貨或報廢過多，要怎麼提醒：
   - 同一樣菜**連續兩天以上**都是缺貨或報廢過多 → 標成「持續現象」，列出每一天的備貨、賣出、報廢、沒買到
   - 資料只有一天 → 只分析那一天，**不推測多天趨勢**
6. 用下面的回報格式回報

## 回報格式

```text
策略檔：
驗算結果：通過 / 第 N 天的 ○○ 對不上（寫出哪個數字）
第 N 天：
  缺貨：菜名 備 … 賣 … 沒買到 … → 建議 …
  報廢過多：菜名 備 … 賣 … 報廢 … → 建議 …
★ 我想多看一個欄位：建議備貨成本（依規則書單份成本，寫出算式，例：招牌鍋貼 13 × 35 ＝ 455 元）
  可執行性：已確認 / 尚無法確認可執行性（缺少哪些資料）
    已確認需要同時檢查：所有菜合計份數 ≤ 80、上架 ≤ 4 樣、
    總備貨成本 ＋ 宣傳費 ≤ 當天可用資金（都寫出算式）
下一版每天建議的備貨量：
```

## 寫完檢查

- [ ] 每一個數字都能在盤點資料裡找到
- [ ] ★ 我再加一條檢查：每個原始數字都是非負整數、`sold` 沒有超過 `stocked`、`waste` ＝ `stocked − sold`；`status` 和 `suggest` 也依規則書重新核對過（缺貨＝賣完後有人沒買到；報廢過多＝報廢 5 份以上；建議＝賣出 ＋ 沒買到）。所有算出來的數字都附算式

## 不准做的事

- 不准修改任何檔案（這個 Skill 只讀不寫，要改策略交給 result-review）
- 不准自己編數字，或用「大概」、「差不多」帶過
- ★ 我再加一條：原始數字只能來自使用者給的盤點資料或上面「資料從哪裡來」列的來源；分析結果只在對話裡回報，不新增檔案、不操作遊戲；缺少份數、成本、宣傳費或資金資料時，要寫「尚無法確認可執行性」，不能把單一道菜的建議當成已驗證的完整策略
